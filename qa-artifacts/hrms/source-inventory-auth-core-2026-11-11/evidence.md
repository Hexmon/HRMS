## High-impact sequences and test gaps

1. **False-success logout on revocation failure (source-confirmed P1 mechanism, existing owner).** Submit a valid bearer or cookie JWT to row 160 while `ValkeySessionStore.revoke` rejects on GET/SET. The route catches that error inside the JWT-validation catch, clears browser cookie, returns `200 {status:"ok"}`, and does not revoke the server session (`A/routes.ts:69-90`; `A/service.ts:815-817`; `auth/index.ts:100-111`). During the Valkey outage a protected request may fail on `sessionStore.get` (`plugins/auth.ts:73-82`); after service recovery the still-unrevoked JWT may work until expiry. This is not an executed outage result. `__tests__/contracts.contract.test.ts:948-1135,1497-1521` covers successful bearer/cookie revocation and missing/stale sessions; targeted search found no injected revoke-failure case. AUTH-S25-002/TEN-S25-019 should explicitly distinguish malformed/stale JWT idempotency from valid-JWT revocation failure and avoid claiming success on the latter.
2. **Company and proof activation gap (existing P0 scope).** A new signup can verify mailbox and receive a company-bootstrap capability, then become first Admin via row 164 (`A/service.ts:315-373,518-582`) without DEC-030 platform company/domain approval. HR can create or activate an employee and enable setup (rows 176, 182, 184); set-password can mark employment active (row 156) without DEC-007 verified documents and DEC-046 verified personal email. These are source-confirmed missing gates, not executed fraudulent onboarding. AUTH-S25-001/002, TEN-S25-003/031, MAIL-S25-008 and BIZ-S25-007 own the vertical activation oracle and approved founding-Admin exception.
3. **Historical and hierarchy ownership.** Current core user scoping is a real mitigation (`C/service.ts:876-909,1191-1222`) but uses mutable current preference; past-company audit/retention requires captured provenance under DEC-004. `updateManager` globally rewrites matching prefixes (`:1276-1297`) and subtree resolution selects global prefix matches (`:786-795`). With future company-scoped duplicate employee codes or corrupt historical paths, another tenant's descendants could be affected; this remains conditional until isolated A/B and migration data tests. CORE-S25-002/TEN-S25-002/004/033 already cover it.
4. **Credential, invitation and storage ordering.** Signup/reset/resend send before durable auth state commit (`A/service.ts:234-260,437-490,1118-1158`); login creates a session without validating active company first, while later protected requests check company context; GET `/me` can mint an unpersisted resume token. Core login-enable generates a setup token tied to the first active company and reports no invitation delivery. Logo/photo replacement deletes old objects before the new pointer is durably committed. These map to AUTH-S25-001/002/003/004, TEN-S25-021/022 and R2-S25-002. No provider or DB failure was injected.
5. **Existing tests and unknowns.** `auth/__tests__/auth-security.unit.test.ts`, `auth-email-delivery.unit.test.ts`, `auth-session-preference.unit.test.ts`, `auth-remediation-security.unit.test.ts` cover many normal, cooldown, company-switch and role-revocation cases. `core/__tests__/core.unit.test.ts:26-329` covers selected company scoping, last-Admin protection and exports; `core.integration.test.ts:148-408` covers lifecycle/roles/photos. They do not establish the full independent-company setup, verified proof/personal-email gate, two-replica rollback, platform review, real mail delivery, corrupted-prefix isolation or Valkey revoke-failure result. Tests were read, not rerun.
