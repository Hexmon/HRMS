## Findings and boundaries

1. **High-priority existing-card gap:** rows 361–362 have a concrete global config/eligible-user mechanism, not merely a speculative missing filter. The read can leak cross-company identity metadata (including email, `P/service.ts:280-299`) to allowed role holders; the write lets an A Admin choose B finance actors and alter the shared config. This belongs under TEN-S25-005/016 and needs an A/B SQL + fresh-app test. Version checks prevent stale writes but do not establish tenant ownership. The source establishes the mechanism; no current live customer exploit or hosted behavior was tested.
2. **Original-company attendance history:** rows 105, 109–111 and 117 use current preference membership for dated A shifts/reviews. The approved policy retains A ownership after transfer; the present resolver would likely deny or hide A history once the person is assigned to B. This is conditional on a valid transfer fixture, which the current single-preference model cannot faithfully represent. Refine TEN-S25-002/016 and attendance historical acceptance; decide correction authority. Existing unit tests cover termination and direct B user denial, not approved transfer.
3. Device routes have server-derived company and SQL company predicates, lock-based state changes, and relevant integration tests. That is a source mitigation, not clearance under stale sessions or concurrent transfer. The public webhook is signature guarded, but new company-owned provider design requires a scoped event ledger and multi-instance callback ordering under MAIL-S25-007. Dashboard history is already TEN-S25-013. No genuinely unregistered P0/P1 card is asserted from this bounded pass.

Source tests above were read, not executed. No browser, production-like load, transfer runtime, hosted setting, provider callback or SQL attack probe was performed. The remaining inventory is not cleared; cumulative distinct route count after this pass is **203**, not the entire 444-row inventory.
