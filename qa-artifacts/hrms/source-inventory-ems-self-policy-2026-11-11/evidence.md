## Source-derived failure sequences and limits

1. **Foreign employee and policy records.** In an isolated two-company fixture, A HR/Admin can request B employee letters or proofs by `user_id`, acknowledge a B letter by ID, or update B's global policy by ID. The source lacks an immutable company predicate at the named service/repository boundaries (`ems/policy.ts:5-28`; `ems/service.ts:382-473,475-544`; `ems/repository.ts:242-288`). A Auditor can list B proof metadata through row 245, subject to classification policy; Auditor is not granted document write. A/B existence, response and persistence have not been executed here. EMS-S25-001/002 and TEN-S25-006/016 already cover the authorization repair.
2. **Policy publication and acknowledgement drift.** A user's v1 acknowledgement remains keyed to the same policy ID when HR/Admin updates content or `version_label` in place, so a material v2 may still appear acknowledged. `ems/service.ts:414-473` and `db/schema.ts:2682-2716` support the mechanism. `BIZ-S25-022` already owns immutable published versions per DEC-029; exact materiality and effective deadlines remain DEC-BQ12. The policy list currently also includes active policies with future effective dates; publication/effective-date semantics need the pending business decision.
3. **Read-side state creation.** `GET /ems/profile/me` can create an in-memory default profile (`ems/repository.ts:90-120`), and `GET /ems/policies` can create in-memory pending acknowledgement rows (`:290-314`). `app.ts:278-280` suppresses persistence for GET. They may be flushed by a later mutation's selected write set, but durable creation at the read boundary is not guaranteed. This is a source-confirmed persistence/lifecycle refinement to EMS-S25-001/002 and ARCH-STATE-014, not a separately registered P0/P1 here. A controlled reload/two-replica test should establish actual user-visible drift and uniqueness behavior.
4. **Proof upload and replacement.** A foreign HR/Admin target can select a B user through row 246; same-target replacement checks constrain a random other employee's document but not company. The new object upload precedes owner assignment and replacement mutation (`ems/service.ts:489-530`); `app.ts:336-398` selects returned new document ID for EMS flush. The already documented old-proof flush omission may let a replaced proof reappear after reload. That is an existing TEN-S25-021/R2 finding, not a new one. A failed upload, old proof access, and DB/restart outcomes require isolated testing.
5. **Test coverage seen, not rerun.** `hrms_backend/src/modules/ems/__tests__/ems.integration.test.ts:18-135,139-242,324-463` exercises self profile/version, selected letter/policy acknowledgements, policy edit and one-company E1/E2 proof denial. This pass found no independent A/B HR/Admin/Auditor fixture, foreign letter/policy ID denial, material v2 re-acknowledgement, read-side reload behavior, or old-proof replacement after durable reload in that suite. Tests, migrations, hosted providers and all other inventory rows were not run or certified.

**Disposition:** 11 selected unreviewed API rows traced. No distinct unregistered P0/P1 established; existing EMS, document, policy-version, email-verification and state architecture cards need the refinements above. Inventory CSV remains unchanged.
