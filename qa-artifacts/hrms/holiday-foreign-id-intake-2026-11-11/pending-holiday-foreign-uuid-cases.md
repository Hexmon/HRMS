## Source trace and why this is a collision

1. `hrms_backend/src/modules/leave-wfh/index.ts` registers the routes under `/api/v1`; `routes.ts:183-194` is `PUT /api/v1/holidays/:id`, with the UUID from the URL and `holidayUpsertSchema` body. `policy.ts:8-28` allows assigned Admin/HR Manager roles. `service.ts:441-459` resolves the actor's company, passes it as `company_id`, appends `holiday.upserted` to the outbox with aggregate UUID and version, and returns the holiday. The event payload names holiday ID, actor, date and region, but has no explicit company ID.
2. `repository.ts:156-201` finds an existing holiday by **both** UUID and actor company. If A's HR supplies B's existing UUID, `findHoliday` returns null, then the create branch pushes another in-memory record with the same UUID under A. The duplicate-name check excludes the same UUID, so it does not reject this path. `expected_version` is only checked when `existing` belongs to A; providing B's UUID can bypass the intended version check. The caller may see an A-owned 200 response in memory; this is source inference, not observed HTTP.
3. `postgres-data-store.ts:4795-4820` loops over hydrated holidays and runs `INSERT ... ON CONFLICT (id) DO UPDATE` for each. On conflict, it updates name/date/region/optional/version/timestamp but **not** `company_id`. The database UUID primary key and company/date/name unique index are in migrations `0004_leave_wfh.sql`, `0027_company_scoped_holiday_uniqueness.sql`, and `0028_finalize_attendance_company_scope.sql`. Therefore a duplicate in-memory UUID cannot become an A row in SQL. Depending on iteration order, the B-owned row may take A's fields, or a later B snapshot may overwrite A's fields. Both violate the authorized A edit result. Exact order and SQL/event outcome require a real isolated execution.
4. The holiday URL does not match the `/api/v1/leave-wfh` domain flush prefix in `app.ts:244-259`. A successful PUT selects the **full flush fallback** (`app.ts:278-310`), which calls `flushPlatform` and `flushLeaveWfh` within one transaction (`postgres-data-store.ts:648-672`). `flushPlatform` writes outbox events (`:3283`, `:3416-3463`) before `flushLeaveWfh`; a SQL error rolls back. No runtime proof here that a particular event and row committed or that the process snapshot recovered after a failed flush.
5. `repository.ts:203-214` lists by company, but `leave-wfh/service.ts:571-576` and `timesheets/service.ts:839-846` build nonoptional holiday date sets from **all** companies. Attendance filters by company at `attendance/service.ts:4627-4655`. `reports/service.ts:556-563` also maps all loaded holiday rows into a report. Thus a corrupted holiday and broad calendar consumers can affect leave duration, timesheet expected hours, attendance classification, and report output differently. DEC-008 requires the employee's assigned office calendar; DEC-Q11 still leaves effective-date office moves open.

**Existing tests:** `hrms_backend/src/modules/leave-wfh/__tests__/leave-wfh.integration.test.ts:141-240` covers an Admin creating a new random UUID and an Employee getting 403 on its update. A source search found no foreign UUID A/B collision, two-instance reload, SQL row/event comparison, or injected rollback case in that suite. This is coverage observation, not a claim about all tests in the repository.

**Backlog links:** Primary `TEN-S25-016` (resource/related-ID authorization after company resolution), linked `TEN-S25-014` (leave/WFH persisted ownership) and `TEN-S25-025` (assigned-office calendars). The latter has an unresolved DEC-Q11 branch oracle. Use this as a new task-specific leaf under the appropriate owner allocation; do not claim that the broad existing `S25-044-*` cases already execute the UUID collision.

### Leaf 1 — Foreign UUID denial and no durable side effects (API/SQL; Failed in focused local probe)

**Given** `H_B` exists under B and A HR/Admin knows its UUID, **when** A sends `PUT /api/v1/holidays/H_B` with valid A-looking name/date/region/optional values and with no version, B's current version, or a stale version, **then** the approved API contract must deny the foreign identifier (403 or indistinguishable 404, to be fixed by owner) before mutation. No A duplicate with `H_B`, B field/version change, `holiday.upserted` success event, or false success. B may still read and edit its original holiday. Compare SQL and outbox after the denial and after a second-instance reload; compare A/B GET for the target year. Also check a random unknown UUID follows the approved create contract without revealing whether a foreign UUID exists. Re-test a foreign ID while A already has a duplicate name/date/region to confirm the rejection is based on ownership, not coincidental uniqueness.

### Leaf 2 — Valid same-company update and duplicate-name/version boundaries (unit/API/SQL; Not Tested)

**Given** `H_A` belongs to A, **when** A HR/Admin changes it with the current `expected_version`, **then** exactly A's row changes, version increments once, B's rows stay byte-for-byte unchanged, and one correctly owned `holiday.upserted` event records the committed aggregate/version. Reusing the old version must conflict without an event. A second A holiday with the same company/region/date/name must conflict according to the database rule. Test same date/name in B as an allowed independent record. Use the approved default/required version semantics; current optional version permits a no-version update, so whether it must be mandatory is an owner/implementation question. Validate region and date boundaries and reject client-supplied `company_id`, `version`, or protected status fields if present.

### Leaf 3 — Two-instance collision, commit/event consistency and retry (SQL integration; Not Tested)

**Given** instance 1 and instance 2 loaded from the same isolated SQL fixture, **when** A HR attempts B's UUID, then instance 2 reads immediately and both instances restart/reload, **then** all views and SQL agree on a denied/no-effect outcome. Inspect the real SQL row owner and fields, not only the first handler's 200/response. Check whether a `holiday.upserted` outbox row was committed with B's aggregate UUID despite a B-owned SQL row, and whether payload/tenant identity identify A or B; no worker or report should consume a false success. Repeat with simultaneous A and B updates to `H_B` and reversed row insertion order. An authorized A update and B update to their *distinct* UUIDs must remain independent. A lost response after a committed A update followed by retry must not overwrite a newer B row or create duplicate logical events; define the version/idempotency contract before final assertion.

### Leaf 4 — SQL failure and process-memory rollback (failure integration; Not Tested)
