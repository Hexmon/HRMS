# Per-Feature Case Design, Execution And Tracker Handoff

Standing owner instruction, 2026-11-11: use this reference in plan/incremental mode for every new feature, behavior update and defect in every sprint; Sprint 25 is only an example. During requirements discussion, present concrete allowed, rejected and failure/recovery scenarios with their expected outcomes, ask material unanswered business questions, and refine the cases as rules change. Discussion-only work stays planning-only and does not authorize implementation or application execution. It extends the existing QA skill; it never authorizes product tests or makes an unknown oracle approved. Read docs/agent/test-and-qa-completion.md and the affected source at the actual revision.

1. **Trace the slice before coding.** Follow rendered control/API/worker entry through current actor and all assigned company roles, resource authorization, validation, policy/state machine, transaction/constraints, cache/queue/provider, audit/outbox, reports and the refreshed user view. Record file/symbol and missing links. UI role mode does not restrict the backend role union (DEC-031).
2. **Build a decision table from approved intent.** For each rule identify allowed/denied actor, company, related object, initial state, input, transition, output/error, durable side effects and forbidden effects. Do not copy current defects into expected results. Label implemented/inferred/unknown rules; unresolved acceptance stays TBD — NEEDS_BUSINESS_CONFIRMATION with a named owner/question. Review the current decision log rather than assuming older mail/payroll rules still apply.
3. **Partition deliberately.** Consider valid, missing/null/empty, type/encoding, minimum/exact/maximum, configured L-1/L/L+1, unrelated same-company/foreign IDs, wrong role, stale session/version/tab, every valid/invalid transition, duplicate/reordered delivery, concurrent decisions, commit failure, timeout/ambiguous success/restart/retry, office/calendar/clock, malicious uploads/exports and dependency outage. For broad spaces add properties or model tests with independent oracles. Record N/A with rationale; one case listing partitions is a starting charter, not proof that all branches were tested. Apply the 19 adversarial categories in references/security-and-privacy.md and the HRMS overlay.
4. **Write executable cases, not titles alone.** Give stable Case ID + Task ID, risk/priority, actor/context, synthetic fixtures/preconditions, concrete steps, visible and durable expected result, forbidden effects, source/approved oracle, open question, test layer, owner and status. Use assets/test-cases-template.csv; keep the 12 standard planning outputs. Split a case when outcomes or failure mechanisms differ. New Sprint 25 examples live in qa-artifacts/hrms/sprint-25-test-design-2026-11-11/; refine them against each implementation, not as immutable generated truth.
5. **Select the right layers.** Unit-test extracted validation, decisions and calculations using independent expected values; component tests exercise loading/error/accessibility and stale responses; real integration tests establish SQL transactions/RLS/locks, Redis atomicity/expiry/recovery and queue/provider boundaries; Playwright exercises rendered real-user workflows. Scripts calling APIs are not browser verification. Source/diff branches determine required cases, not a fixed number per ticket. Missing frontend unit or changed-line tooling remains QA-S25-003, never an invented command.
6. **Run after each authorized behavior slice.** Add a failing-before/passing-after regression for a bug when reliable. Run targeted tests, appropriate package gates and affected integration/browser cases. After new changes rerun affected checks at the exact head; diagnose flakes and retain failures. Measure all added/modified executable lines and changed business/security branches under the completion policy; no ignores, weakened assertions or fake mocks. Unchanged docs/types/generated outputs need justified N/A, not artificial unit tests.
7. **Review and close truthfully.** A separate authorized reviewer checks requirements, diff, test assertions, branch inventory and actual results. No delegation means prepare an independent human handoff; self-review cannot satisfy independence. Required Failed/Blocked/Not Tested cases or missing tooling/oracles/review keep the task pending. Generated cases, counts or screenshots alone never mean Done, human UAT or penetration certification.

## Shared Sprint Execution View

Follow docs/process/task-tracker.md and the owner's authorization. When creating or materially updating a behavior task, publish its complete cases in the same shared workbook at the same time. Use the existing case-detail view or one filterable Sprint N Test Cases tab where needed, and link the task row to its exact case rows. Inline full bodies are acceptable for a small task if readable. Case titles, a case count, "QA planned" or a repository-only link do not satisfy publication. Each body needs the actor/company/state, preconditions and synthetic data, reproducible steps, explicit visible/durable/forbidden-effect oracle, layer, risk/priority, approved source/open question, owner and execution/evidence fields. Match the existing case schema; do not overwrite history. Parent rows link to child cases without duplicate estimates. If access is unavailable, retain the full pending rows locally and report them; do not claim the sheet was updated. Reconcile cases when requirements or implementation change, before Ready and again before Done. Preserve historical task status/points and old evidence. New cases start **Not Tested**. At execution add actual result, exact source head/date/environment, sanitized evidence, reviewer and defect link. The general PR phrase Not run maps to the planning CSV status Not Tested; neither means passed. Record Blocked and its question/dependency explicitly where the execution system supports it; do not edit the strict planning-template vocabulary silently.

## Example: Bounded Session Revocation

For TEN-S25-019, sign in on two isolated instances, commit access removal and try both old sessions; race a new login against removal; revoke one session without revoking unrelated users; restart/outage Redis and verify the chosen durable authority and honest failure response. Assert the approved next-request consistency contract and the absence of revived authority or cross-company effects. Exact response/outage policy needs approval. A unit mock of Redis commands cannot establish multi-instance revocation or bounded work.

They cannot approve HRMS business rules or satisfy unit/SQL/QA gates by themselves. Never accept healer changes that skip tests, broaden locators beyond intent or weaken an oracle to obtain green.
