## Device And Finance Governance

`platform/service.ts:registerDevice/listDevices` resolve the authenticated active company; `platform/repository.ts` uses PostgreSQL transactions with `setTenantDbContext`, company-qualified predicates, and a transactional outbox. This is a stronger existing tenant boundary. Device registration, suspension and revocation still need synthetic A/B and retry tests.

`platform/service.ts:getFinanceGovernance/updateFinanceGovernance` instead use `PlatformRepository.getFinanceGovernanceConfig/saveFinanceGovernanceConfig`, which reads or replaces one `store.financeGovernanceConfig` with `scope_key: "global"`. Eligible finance/manager lists iterate all active users, and input approvers are checked for role/status but not actor company. Company Admin A can therefore select a B user at the source layer and the configuration is shared. Verify the route in a disposable A/B environment. DEC-013 requires company-specific finance approvers; DEC-012 requires independent Manager and Finance approvers at expense submission.

## Dashboard And Notifications

`dashboard/routes.ts` resolves an active company and may load a PostgreSQL attendance read model. `dashboard/service.ts` scopes workforce by current user preference, but many metric groups infer ownership through current employee/approver IDs rather than an immutable record company: expense tickets, timesheets, leave/WFH, assets and outbox. A transfer can reassign historical counts to the new company or omit unassigned assets. This is a source-based consistency risk; compare response counts with company-owned ledger rows before claiming an observed leak. The summary also returns `unavailable_features` saying helpdesk and project utilization APIs are not implemented, while both modules have routes and tests in the source. That text is stale and may mislead users.

`notifications/repository.ts` filters list, unread count and mark-read by `target_user_id`, so another user's notification ID is rejected at this service seam. Source search found direct notification creation in expense service, not in helpdesk/timesheet services; the notification presenter has title fallbacks for those event types, which does not prove delivery. Check requested notification coverage, action URL authorization and retry behavior. The `status` value changes from `pending` to `sent` when read; this is the current implementation's terminology.

## Frontend To API Trace

The `/admin-settings/security`, `/email-templates`, `/workflows` and `/roles` routes use the `@/domains/admin` query/mutation adapters when the API route gate is enabled. On a successful security save, the screen also writes the returned value to the provider's browser-local state. The provider initializes company, master data, roles, workflows, policies, templates, channels, security and audit from unscoped `hawkaii_admin_*_v1` localStorage keys. Those keys support mock mode; the API-backed screens use server query data, and production forces mock API fallback off in `shared/api/config.ts`. Authentication clears the React Query cache on logout. Test the actual user-visible stale-tab and failed-save behavior before calling the browser state a security boundary.

The security screen describes password rules as enforced at signup/reset/admin-set, and the backend `auth/service.ts` consumes `adminSecuritySettings` for password checks and session TTL. `plugins/rate-limit.ts` also reads `login_attempt_limit` before login; company-specific policy therefore needs a documented way to identify the company at pre-authentication and a platform minimum. The email-template screen saves through a versioned Admin mutation; `email-delivery-service.ts:templateFor` currently selects by template key with no company context. Static search found no operational read of the saved Admin workflow and notification-channel arrays, so the target migration must include actual consumer wiring and verification, not just company IDs on settings rows.
