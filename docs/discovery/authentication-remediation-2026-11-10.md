## Proposed Architecture And Alternatives

Keep the modular monolith, Fastify and PostgreSQL. Use request-scoped SQL repositories for security state; domain policies remain responsible for resource ownership and workflow rules. Browser navigation, JWT role claims, cached process collections and email delivery telemetry do not establish authority.

| Choice | Benefit | Limitation / decision |
| --- | --- | --- |
| Redis per-user session index only | Removes global `KEYS` at modest implementation cost | Does not atomically couple credential/role/company state to revocation, or repair stale PostgreSQL writers. Insufficient as the final repair. |
| PostgreSQL sessions plus monotonic account authorization version | One transaction boundary for authority, durable per-session logout, straightforward replica correctness | Adds indexed reads and requires all legacy auth/core writers to be retired. **Recommended**, with measured pool/query budgets. |
| Managed identity provider | Can supply supported MFA/OIDC/session primitives | Does not decide HR lifecycle, tenant ownership, documents or approval authority. Provider/data/cost choice is pending; not a prerequisite for direct bug repair. |
| Short-lived stateless JWT alone | Fewer session reads | Revocation waits for expiry and cannot satisfy the proposed next-request denial invariant. Retain tokens only as session locators with current authority checks. |

### Request And Command Boundaries

1. Apply bounded ingress/body/connection admission and an early IP/service budget before costly authentication. Trust only the verified deployment proxy chain; avoid a trust-all production default. Apply account/company/purpose budgets where that context is resolved server-side. Public account responses remain enumeration-safe.
2. Validate the token using a maintained JOSE implementation with explicit algorithm, exact structure, claim types, expiry, issuer/audience and a configured key policy. A malformed parser is a hardening issue; no unsigned-token acceptance was established by this review.
3. Read the session JTI and current account/company/employment/roles from indexed PostgreSQL queries. Compare the issued authorization version and current version. Keep the actor snapshot request-local. Effective permissions are the union of all current company-owned assigned roles (approved AUTH-Q02); the selected UI role is presentation context only. Cache permission definitions by tenant/policy version only if invalidation and denial semantics are proven; initially avoid positive session-authority caching.
4. For sensitive writes, enforce resource company, allowed action, related IDs, independent approver and current role/status within the transaction. Serialize relevant role/lifecycle changes and competing commands through a consistent account/aggregate lock order or version predicates. A request authenticated before a later revocation must not gain an unlimited in-flight write window.
5. Commit targeted business/security changes, token consumption, audit and exact outbox IDs together. Return success only after commit. External email, file processing and Queue sends happen outside the transaction through durable intents. Do not hold SQL locks across provider calls or expensive password hashing.
6. Login verifies a fetched credential asynchronously, then locks/rechecks its version, account status, company and policy before inserting a session. Revocation locks the same account and increments authorization version. A concurrent login either uses current authority or fails/retries; it cannot resurrect pre-change authority.
7. Logout conditionally revokes the supplied session in SQL. Invalid/already-revoked tokens can be idempotent; a durable-store failure is reported as unavailable, while the local cookie can still be cleared. Distinguish browser-local sign-out from confirmed server revocation.

### Registration, Recovery, Invitations And Mail

- Reserve company/account authority transactionally; unauthenticated retries cannot overwrite another request's password/name/ownership intent. Prefer collecting the password only after mailbox proof through a restricted secure continuation. Resend rotates delivery under the same immutable owner/company binding.
- Setup/reset changes credentials only when the challenge, login entitlement, employment state and required-document policy permit it. Password completion does not activate employment. Admin disable/termination/transfer revokes incompatible capabilities and sessions transactionally. Required proof evaluation uses policy version and current verified evidence; a replaced proof cannot race activation.
- Use purpose-specific HttpOnly continuation sessions for browser setup. Prefer a same-site browser API/session topology, subject to the later deployment design. Verify Vercel/Render cookie/Origin behavior rather than assuming cross-site cookies work. Preserve explicit bearer/API clients through a separately documented exchange; production never exposes successor secrets through `dev_only` or Web Storage.
- Invitation acceptance, employee setup, first-founder setup and password recovery have distinct purposes and permissions. Bind invitations to the real company account and email; never choose the first/last company. Reject unimplemented `invite_token` behavior until a real contract exists.
- Commit challenge plus delivery intent; deliver after commit with idempotency, bounded retry, stale-generation checks and cancellation/supersession semantics. Provider success followed by uncertain persistence is reconciled. Do not destroy a usable link merely because a replacement provider call failed; define exactly which generation remains usable under the chosen policy.
- Persist every supported onboarding field or explicitly identify it as a preview. Version and record terms acceptance if the product requires it; legal content/acceptance requirements need owner review. Empty, invalid, expired, already-used, offline and server-unavailable states must remain distinguishable in the UI without public account enumeration.

### Distributed Abuse And Resource Controls

Refine TEN-S25-028 rather than opening a duplicate limiter ticket. Use atomic supported Redis scripts for increment/expiry and related budgets; do not assume newer Redis commands are supported by Upstash/Valkey. Namespace by environment, version and purpose; use keyed hashes for normalized account identifiers. Combine account-target, source/prefix, company and overall budgets without exposing existence, globally locking a victim account, or applying one office IP allowance as an account lockout. Count failed/expensive work deliberately; successful login and reset-email budgets have different purposes. Protect QR, onboarding uploads, unknown routes and bad-token paths as well as login.

Define Redis failure behavior per route: security-sensitive public auth/mail operations should use a controlled, observable unavailable response when shared enforcement cannot be guaranteed; protected sessions remain subject to PostgreSQL authority. Any bounded emergency fallback needs an approved policy, expiry and evidence across replicas, never silent unlimited bypass. Set retry/deadline/queue limits and test reconnect storms. Fix expired memory-bucket cleanup for supported local mode; do not use process-local fallback as a distributed guarantee.

Bound asynchronous hashing concurrency and input bytes; benchmark before tuning KDF cost. Enforce endpoint-specific multipart/part/file/pixel/deadline limits before expensive work. Reuse R2-S25-002 validation and shared upload intents. Public QR field visibility remains DEC-016; abuse controls do not silently change its approved response contract.

### Privileged Password Recheck

The owner approved password recheck for sensitive Admin/HR/Finance actions and deferred MFA. Add a protected-action matrix covering role/security/lifecycle changes, sensitive proof operations and financial/payroll finalization as proposals for precise review. Recheck uses the account’s current credential through bounded asynchronous verification, then creates a short-lived server-side assurance bound to account, company, session, auth version and permitted action/intent. Enforce it with tenant/resource/workflow authorization inside the mutation transaction; consume action challenges atomically where required. An assurance from company A, an old credential/version, another session or a revoked role cannot authorize company B or a later action. Define approved lifetime/reuse and lost-response recovery; never cache raw passwords or treat a UI modal as enforcement. Test wrong/current/changed password, brute attempts, cancellation, replay, expiry, concurrent role revocation and employee self-service unaffected by privileged-role membership. No MFA provider is selected or implemented.

## Verification, Recovery And Tracker Contract

- Unit: meaningful input/error/output/side-effect assertions and every changed branch; test new direct-bypass cases, known-token states, normalization, unsupported fields and dependency failure. Use QA-S25-003 changed-line tooling before claiming its gate.
- Integration: real isolated PostgreSQL/Valkey, two API instances, explicit SQL locks/constraints/RLS, concurrent token consume/lifecycle/permission changes, commit rejection, restart and retry. Mocks prove control flow only.
