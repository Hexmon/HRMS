# Session, Rate-Limit And Media Failure Boundaries

Source inspection 2026-11-09 at `6a8d11f7`. These are **source-supported risks and verification gaps**, not hosted findings or an executed outage/Cloudinary test. No credentials or raw files were accessed. The current branch makes no runtime change.

Follow-up 2026-11-10 at `87618f88`: [Document storage review and proposed R2 design](r2-document-storage-remediation-2026-11-10.md) traces additional consumer/persistence/replacement/idempotency/audit/content-processing gaps and refines Sprint 25 tickets. Owner direction is complete Cloudinary removal in favor of R2 before launch. The proposal uses private storage, targeted SQL transactions, durable upload/purge intents and bounded reconciliation; it is not implemented by this documentation update. The original dated findings below retain their original evidence scope.

| Boundary and affected user | Current path | Persisted invariant / failure | Detection and recovery test |
| --- | --- | --- | --- |
| Role removal, deactivation or password reset should terminate old sessions | `core/service.ts` and `auth/service.ts` call `sessionStore.revokeUser`; `auth/index.ts:ValkeySessionStore.revokeUser` uses `KEYS hrms:session:*`, then sequential `GET`/`SET KEEPTTL`. `plugins/auth.ts` calls `get` for each protected request and reads actor from the process store. | Revocation cost grows with **all** live sessions, not just one user's sessions. The scan/update is non-atomic; concurrent session creation and multi-instance cached actor state need a race test. Source does not prove a stale-session exploit. | Measure revocation at increasing session counts, inject Valkey errors and concurrent login/role change across two API instances, then assert old-token denial at next request and audit result. Use a user-indexed or versioned session scheme with bounded revocation and reconciliation. |
| Login and public QR abuse control | `plugins/rate-limit.ts` uses a per-user or IP key. PostgreSQL mode uses Valkey `INCR`, `TTL`, `EXPIRE` in separate commands; memory mode uses a process-global Map. `app.ts` sets Fastify `trustProxy` from configuration and hosted examples set it true. | Distributed abuse across IPs is not bounded per account/company; proxy-chain trust and Redis-outage behavior were not exercised. A Valkey command error appears to propagate rather than silently allow, but the actual HTTP response and operational impact are unverified. | Test known proxy hops, spoofed forwarding headers, distributed IPs, username/account buckets, Valkey outage, retry and recovery. Compare counters across replicas; measure false positives. A single atomic Valkey operation and clear outage policy should be specified. |
| Verified raw proof download should require current authorization | `documents/service.ts:downloadUrl` authorizes once, then returns stored `object_url`/`cloudinary_url` if it is HTTP(S), with `expires_in_seconds: 900`. `object-storage.ts:putObject` stores Cloudinary `secure_url`; `presignedGetUrl` constructs a plain Cloudinary URL and ignores its expiry argument. `isBrowserOpenableUrl` only checks the scheme. | The response advertises a 900-second lifetime without code-level URL expiry/signing. A copied direct URL may outlive permission revocation and bypass future access-log checks **if the provider serves it directly**. Actual provider access controls and deployed resource configuration have not been checked. DEC-011 limits raw proof viewers. | In an isolated provider fixture, issue a URL, revoke viewer access, wait beyond 900 seconds, then request it without an HRMS session. Verify response, cache behavior, no raw proof exposure and audit. Serve protected bytes through an authenticated gateway or a demonstrably expiring signed URL; record rotation/revocation. |
| Upload should not leave orphan bytes | `documents/routes.ts` buffers multipart parts; `documents/service.ts:upload` calls `objectStorage.putObject` before inserting metadata, versions, log, outbox and optional expense attachment. `app.ts:onSend` later flushes the domain. | A failure after object upload, including invalid expense relation or database flush failure, can leave bytes without metadata. The file may still be addressable by a provider URL. No compensation path is visible in this method. | Force attachment rejection and DB commit failure after successful mock upload, enumerate orphan object keys, then verify cleanup/retry and idempotent recovery. Use staged object state plus a durable cleanup/reconciliation job. |
| Delete should not break existing metadata | `documents/service.ts:delete` removes object bytes before `hardDeletePersistedDocument` starts/commits its SQL transaction, then mutates memory and emits outbox. | If SQL deletion fails after byte removal, metadata can still point to missing bytes. If later outbox flush fails, the DB deletion may have committed without its event. This is a source ordering risk; no failure-injection result here. | Inject object-delete success/SQL failure and SQL success/outbox failure; assert a retrievable or explicitly tombstoned state, event/audit reconciliation and recoverable delete. Prefer a DB tombstone/outbox first and idempotent asynchronous object purge after retention/approval. |
