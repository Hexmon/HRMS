# Changed executable coverage gate

QA-S25-003 adds Vitest V8 coverage for backend unit tests and frontend component tests, plus a PR and deployment-branch changed-diff gate. The gate checks added and modified `.ts`/`.tsx` lines under `hrms_backend/src` and `hrms-client/src`, including every line in a new source file. It maps those lines to Istanbul statement/function locations and every overlapping changed decision-branch span in the generated `coverage-final.json` reports. A missing source location, zero count, missing report, modified report, dirty/stale source tree, unknown base or uncovered branch fails the gate. The gate also scans the full changed file list: deleted source, runtime replaced by non-executable lines, source symlinks or mode/type transitions, new or modified source without text hunks, unknown source-tree assets, and executable/config files outside instrumented source fail as unmeasured rather than passing an empty denominator.

## Run locally

Use a committed, completely clean task head and the real target branch or commit as base. Install each package from its lockfile, install the pinned Python coverage runner, then use the repository wrapper:

```bash
pnpm --dir hrms_backend install --frozen-lockfile
pnpm --dir hrms-client install --frozen-lockfile
coverage_venv="$(mktemp -d)/hrms-coverage-python"
python3 -m venv --copies "$coverage_venv"
export HRMS_COVERAGE_PYTHON="$coverage_venv/bin/python3"
"$HRMS_COVERAGE_PYTHON" -m pip install --disable-pip-version-check coverage==7.11.0
node scripts/agent/changed-coverage.mjs --run-full-suite --base origin/release-01 --head HEAD
```

The backend unit command needs the isolated test environment described in `docs/agent/environment-safety.md`. The wrapper captures the immutable 40-character HEAD SHA at entry, requires the requested head to resolve to that SHA, and creates a detached exact-commit checkout for every generator. Tracked files and directories in that checkout are made read-only as an accidental-mutation guard; installed package dependencies are linked from the clean launcher checkout. The wrapper rechecks both checkouts against the captured SHA and complete Git cleanliness before and after every child command and before every collect, stamp and verify phase. These checks catch stale input, persistent mutation and ordinary commit substitution. They are not an operating-system security boundary: candidate code running as the same user can change permissions or forge writable coverage artifacts transiently. The final verifier receives the captured SHA, never symbolic `HEAD`.

The worker uses canonical executable paths resolved before launch: the running Node binary, `pnpm`, and a regular non-symlink Python interpreter with exactly coverage 7.11.0. CI supplies Python through the explicit absolute `HRMS_COVERAGE_PYTHON` path to a runner-temporary virtual environment created with `venv --copies`; candidate `PATH` entries cannot replace that selection, and the workflow does not widen `GITHUB_PATH` for Python. Local runs may use the same variable as shown above; without it, fallback discovery still requires a canonical regular executable and exact module version. The worker receives fixed `NODE_ENV=test`, `APP_ENV=local`, a synthetic loopback `TEST_DATABASE_URL`, an intentionally absent `HRMS_ENV_FILE` under the temporary output root, and a small operating-system/tool whitelist. It does not inherit ignored `.env.test`, database credentials, `VITE_*` values or arbitrary ambient configuration. Unit tests use in-memory stores and do not connect to the synthetic URL. The separate backend integration/contract/E2E jobs still use disposable PostgreSQL and Valkey. The wrapper creates a unique temporary directory outside the Git worktree, launches the generator worker under Node V8 coverage, waits for that worker to exit and flush its own coverage, then builds, stamps and verifies all three reports in the parent collector. Child suites use isolated coverage destinations; in particular, the gate regression child cannot inherit the full-suite output variable and Python/Vitest children cannot write into the orchestrator's raw V8 directory. The wrapper refuses any tracked, staged, deleted, renamed or untracked worktree/index change. At the checked boundaries, the captured commit identifies every tracked file—including helpers, configs, setup hooks, arbitrary `tsconfig` inheritance and runtime loader forms—without attempting an incomplete language-specific dependency parser. Temporary reports and the detached checkout are removed in `finally` on success or failure. Pass `--coverage-output /absolute/outside-repo/path` or `--preserve-coverage` only when retained diagnostic artifacts are explicitly needed. Rerun the wrapper after every commit. CI checks out the actual PR or deployment-branch push head with full history, then runs the same wrapper. The Render deployment job requires the push coverage job to pass, but an ordinary candidate-controlled workflow status is diagnostic, not the protected trust anchor described below.

Instrumentable programs outside the product source roots use a third report in the wrapper's temporary output directory. CI merges raw Node V8 coverage through AST/source locations, isolated Vitest V8 coverage for external TypeScript and coverage.py executable lines/arcs for Python. Each stamp records the exact HEAD, report digest and covered-source digests. A clean whole repository and exact HEAD identify the tracked input snapshot used by an ordinary run; they do not authenticate reports against malicious candidate code executing as the same user. Before a report or source is read, its lexical path, every path component, real path, filesystem type and Git mode are checked; report artifacts must be regular files outside the repository, while covered sources must be tracked regular files at canonical in-repository paths. Source/report symlinks, intermediate symlinks, gitlinks, normalized aliases, mismatched embedded paths, malformed maps/counts and stale digests fail closed. Counts must be finite non-negative integers, and only a strictly positive count is covered. A changed external JS/TS/Python program with no exact report entry is uncovered. Root or nested `node_modules` files and config-style TypeScript are not accepted through this numerical path.

Workflow, package-manifest, lockfile, runner-configuration and shell changes are not cleared by substring checks, successful neighboring commands, executable mode, or a minimum trace count. Those signals do not prove that each changed semantic node, executable line and decision outcome was exercised: a disabled workflow job or an untraced dangerous shell branch can otherwise pass. Until a trusted, path-appropriate validator provides changed-node/line/decision-specific evidence, every such changed path remains `unmeasured` and the gate fails closed. There is no alternate-evidence allowlist or manual waiver input.

An ordinary pull-request workflow can modify both this gate and the workflow that invokes it, so a required status name from the candidate repository is not a root of trust. The authoritative architecture and one-time owner/admin configuration are documented in [`trusted-coverage-bootstrap.md`](trusted-coverage-bootstrap.md). It uses a GitHub organization/enterprise required workflow pinned to an independently reviewed immutable source revision, or an externally administered GitHub App/CI fallback. The current repository workflow remains diagnostic until that external protection is configured; the bootstrap cannot certify itself.

## Deployment-branch push baseline

On `dev`, `qa` and `main` pushes, comparing only with the immediately preceding commit is unsafe: a failed code push followed by a docs-only push would hide the earlier code and could deploy it. The `resolve-push-coverage-base.mjs` preflight reads successful workflow runs and the named successful coverage job for the same branch, selects the latest validated ancestor, then compares that SHA with the current push head. GitHub API failure, malformed run data, missing history or a nonancestor candidate fails closed. The resolver tests include the failed-code-then-docs-only sequence. `release-*` pushes have no Render deployment job and do not run this push gate; PRs targeting `release-*` still run the PR coverage gate.

There is no prior successful push coverage run on any deployment branch at the time of this task. For the first run, the owner must set the appropriate non-secret GitHub repository Actions variable—`DEV_HRMS_COVERAGE_BOOTSTRAP_SHA`, `QA_HRMS_COVERAGE_BOOTSTRAP_SHA` or `MAIN_HRMS_COVERAGE_BOOTSTRAP_SHA`—to an independently reviewed commit in that branch's history **before** the first push being evaluated. The resolver accepts this bootstrap only after a complete successful API search finds no qualifying run, and only if the SHA identifies a commit object directly and is a strict ancestor of the push head. Annotated-tag object IDs and case variants of HEAD cannot serve as a baseline. Once a successful covered push exists, that run takes precedence; the variable can be removed. Without a trusted bootstrap, the first push fails and Render deployment stays blocked. Setting a baseline to an unreviewed commit would waive changes before it, so record the owner decision and exact SHA in the release evidence. No variable has been set by this task. This workflow does not gate Vercel's separate automatic deployment or the manual Cloudflare workflow; review those controls separately.

The exact HEAD and whole-tree cleanliness detect persistent repository changes at the checked boundaries; source and report digests detect ordinary stale or substituted artifacts. A stamp does not prove that a coverage engine created a report, and same-user candidate code can forge an artifact between checks. CI therefore invokes `--run-full-suite`, whose covered worker exits before the parent collector aggregates its V8 file and then stamps/verifies in the same bounded invocation. Treat this as correctness evidence under review, not cryptographic attestation. Review the CI test log and report provenance; do not treat a standalone `--stamp` as an attestation.

For a stacked branch, record two outcomes separately: `--base <stack-parent-SHA>` measures the task delta and `--base origin/release-01` measures the full submitted PR. A task-local pass does not waive uncovered inherited changes in the cumulative PR gate. A failed cumulative gate leaves the PR draft and the task incomplete until the inherited lines and branches are tested.

## Exclusions and interpretation

- Changed `.unit.test.ts(x)`, other `.test.ts(x)` and `src/test/**` files under either product `src` tree are listed as `TEST SOURCE` when a bounded import scan finds no production import risk. The scan reads committed product source, resolves static import/export, `require`, module `require`, literal dynamic import and configured TypeScript aliases, and fails changed test files when production imports them. Nonliteral module loads, glob loaders, `createRequire`, invalid TypeScript configuration and unresolved local/alias imports also fail closed. This lets ordinary in-source unit tests accompany a covered behavior change. Their assertions still require independent review; test execution alone does not prove quality. Test files outside the two product source trees remain separately listed as `TEST SOURCE`.
- `.d.ts`, interfaces, type aliases, **type-only** imports/re-exports, comments, blank lines and punctuation-only lines have no runtime behavior and are non-executable. Type-only includes declaration-wide `import type`/`export type` and a nonempty named list whose every specifier is inline `type`, such as `import { type A, type B }` or `export { type A }`; TypeScript erases all of these. A mixed named list, a default binding plus inline type specifiers, namespace/value import, side-effect import, value re-export or `export *` remains executable because changing its source or runtime bindings can activate different behavior. When V8 omits a direct location for runtime static `ImportDeclaration` or module-bearing `ExportDeclaration` syntax, the gate attributes only that declaration from a positive real count in the importing module; ESM evaluates its static dependencies before the importer body. It never copies module-level evidence onto an expression statement. An absent importer entry or an importer with no positive count stays red, even if the imported target was executed elsewhere. Dynamic `import(...)`, top-level calls, initializers/callbacks and every other runtime expression require their own direct V8/Istanbul location and fail when uninstrumented.
- `hrms-client/src/routeTree.gen.ts` is TanStack's generated route tree but is imported at runtime by the router. A change or deletion fails as unmeasured and needs build/regeneration evidence; the generated filename cannot clear the gate.
- `hrms-client/src/test/**` contains the Vitest setup harness. It follows the same import check as other in-source test paths; a production import makes its change unmeasured. SQL migrations and other generated/non-TypeScript files require their existing integration/build gates.
- External JavaScript/TypeScript/Python programs are measured when the fresh external report maps their exact changed lines and branches. Workflow/manifest/lock/Vitest-configuration/shell paths remain unmeasured and red unless a trusted path-appropriate validator proves every changed semantic node or executable line and decision outcome. Do not claim syntax, content fragments, neighboring command success, mode or trace counts as numerical coverage or repository-wide 100%.
- Deleting an executable source hunk or whole source file can change behavior with zero added lines. Replacing executable code only with a comment or type is also detected from the old side of the diff. The gate fails these changes and requires explicit regression evidence/owner disposition. A spacing-only edit that retains executable code is not classified as runtime removal.
- A source rename is deliberately analyzed as a deletion and a new file. The new path needs coverage, and the old path remains a failed deletion until its behavior and references are reviewed. A rename is not counted as an automatic 0/0 pass.
- A tracked source file changing between regular file and symlink, any added/retargeted/deleted source-tree symlink or gitlink, a mode-only edit, or a new/modified source path with no text hunk fails as unmeasured. This includes binary and empty new `.ts` files. The gate reads raw Git status and mode before any symlink target for coverage, and disables textconv when reading actual blob diffs. Such changes need explicit regression disposition; a missing hunk cannot silently become 0/0.
- Every changed path under the two `src` trees is classified as measured TypeScript, unmeasured (including unknown extensionless files and assets), or an explicit type-only declaration. `.d.ts` changes and deletions are listed as `EXCLUDED TYPE/GENERATED` and require typecheck evidence; they emit no runtime JavaScript. `.gitattributes` and `.gitmodules` changes are unmeasured because Git attributes and submodule configuration can affect what the gate sees.
- The mode check deliberately treats changed executable shell/config paths, including mode `100755`, as unmeasured by package TypeScript coverage. Executable mode and bounded Bash trace counts cannot clear that state. A trusted shell-specific validator must prove each changed executable line and decision outcome with observable assertions; otherwise the path remains red for explicit independent review.
- The import scan is bounded to tracked JS/TS source under the two product `src` roots and uses each package's TypeScript resolution settings. It does not attest to code outside those roots or arbitrary runtime string/eval loading; changed scripts/config outside the source maps remain unmeasured, and suspicious dynamic module loaders inside product source fail closed. A passing scan is a test-source classification, not a claim that tests have no indirect influence on the application.
- Git patch headers are parsed only before a hunk. A source line beginning `++ b/...` appears in the patch as `+++ b/...`; the gate keeps it inside the current hunk and still attributes later authorization edits to their real file.
- V8 line/branch coverage shows execution, not assertion quality or correct authorization. Review the behavioral oracle and run real DB/worker/browser tests for the affected feature under `docs/agent/test-and-qa-completion.md`.

The report prints exact uncovered source locations and counts. Do not add coverage-ignore comments, broad exclusions or fabricated report entries to clear it. Changed code with an unmeasured executable line or reachable decision branch remains incomplete.

## Manual evidence and independent approval

PR-authored JSON cannot authenticate an owner, reviewer or GitHub review URL. The CI gate **never accepts a manual evidence file as a bypass**; `--manual-evidence` is rejected. Every unmeasured path stays failed in CI. Its exact commands, results and rationale may be attached to the PR for an independent owner decision under protected-branch rules, but that decision is separate from numerical coverage and cannot be represented as 100% by this gate. The external trust anchor required for an authoritative status is described in [`trusted-coverage-bootstrap.md`](trusted-coverage-bootstrap.md).
