# Coordinated Engineering Delivery

Owner-approved operating model, 2026-11-11. Applies to explicitly activated delivery runs and their implementation tasks. The activation supplies authorization for commits, task-branch pushes, PR creation and tracker changes; the workflow alone does not grant those permissions to an unrelated task. The owner merges release-01 PRs and approves later main promotion. Respect conversation/tool constraints, including a side conversation's no-delegation rule.

Read root/package AGENTS, [task tracker](task-tracker.md), [test/QA completion](../agent/test-and-qa-completion.md), [per-feature case workflow](../../.agents/skills/qa-master-checklist/references/feature-case-workflow.md) and [environment safety](../agent/environment-safety.md). Preserve approved business decisions, meaningful tests and all existing completion thresholds. This procedure does not deploy or change hosted configuration.

## 1. Lead, Source Intake And Dependency Order

The lead owns the goal plan, task queue, dependency graph, worktree/branch operations, tracking, PR publication and handoff. Start by identifying the actual repository, worktree changes, remote/base/head, available agents/tools, existing PRs and installed test tooling. Fetch remote state when authorized; never assume the local release-01 is current. Reconcile existing uncommitted work without discarding or sweeping unrelated changes into a new commit. If the approved agent/planning workflow is not on the integration base, prepare an owned workflow/bootstrap PR first and record it as a dependency; do not silently lose these instructions in a fresh worktree.

Reconcile the live assigned backlog and source inventory, including existing Sprint 25 tasks/cases, owner decisions, auth/R2/mail/audit refinements, duplicate findings and already completed historical discovery. Parent/epic rows are rollups, not empty implementation PRs. Record unreviewed source explicitly; a backlog scan is not full application clearance. Separate current implementation, approved target, proposal and unknown.

Prioritize using observed security/data/payroll impact, exposure, dependencies, current owner priority and implementation/test prerequisites. Produce a dependency graph and ordered task table: ID, source evidence, rule/unknown, risk, prerequisites, proposed slice, branch/base, cases, verification, PR, status and owner Anurag Kumar. Explain ordering rather than inventing scores or capacity. Recheck QA-S25-003's missing frontend unit/changed-line tooling and schedule confirmed gate prerequisites before claiming feature completion. Deep-trace each chosen task before coding; do not freeze the queue around stale suggestions.

## 2. Team And Write Ownership

Use actual available agents only. During intake, independent architecture/data, security/API and QA analysis may run in parallel. Implement one coherent task at a time; parallelize bounded reading, case design and independent reviews. Suggested seats are lead, implementer, senior code/security/data reviewer and independent QA; rotate specialist seats within the platform's actual concurrency limit. Do not invent agent identities or approvals. If delegation is unavailable, keep independent review pending for a human.

Only the lead dispatches team agents and owns shared git/tracker operations. Each brief specifies one question/task, permitted worktree/files, approved rules, source references, base/head, dependencies, cases, authorized environment and expected evidence/report. The implementer writes its assigned task worktree; reviewers are read-only and inspect the exact revision plus direct callers/contracts, not only the author's summary. Avoid concurrent edits to shared migrations/generated contracts/fixtures; the lead coordinates their ownership. A reviewer or QA agent must not be the implementation author. Use existing specialist profiles; no hidden recursive team or external paid service is required.

Maintain one durable run plan/ledger with task IDs, branch/fork SHA, parent dependency heads, changed files, decisions, commands, reviewer identity/revision, findings/disposition, commits/PRs, case links, secret blockers and next action. Read it and actual git state after compaction before continuing; do not replay completed work from memory. Give concise progress updates and do useful independent work while an agent or human dependency is pending.

## 3. Per-Task Engineering And Review Loop

1. Trace real UI/API/worker entry through current actor/assigned roles, resource authorization, validation, domain rules, state/transaction/constraints, cache/queue/provider, audit/outbox and refreshed user result. Check consumers, exports, migration compatibility and recovery. Cite precise source evidence; reproduce defects safely where feasible. Never report a suspected or statically inferred failure as an executed result.
2. Discuss concrete success, rejection and edge/failure cases during refinement. Resolve material business questions against approved decisions. Publish full case bodies in the shared workbook with the task, linked to exact rows, under task-tracker.md. Preserve earlier cases/status/estimates and new cases' Not Tested status. Missing sheet access means exact pending rows locally and an explicit publication gap, not a false write claim.
3. Design the complete required slice, considering necessary DB/backend/frontend/API/worker/config/documentation changes. Suggestions in a task are candidates, not commands. Make source-backed adjacent corrections when needed for the same acceptance/security/consistency invariant; record why, add cases and update the task. Independent beneficial enhancements get a separately identified/prioritized task and branch. Do not invent entitlements, privileges, retention or architecture requirements; ask the owner on material decisions while advancing unblocked tasks.
4. Implement with meaningful unit tests and bug regressions, then applicable component/contract/real SQL/Redis/queue/provider/browser tests. Use isolated Docker/synthetic fixtures by default and verify the exact target. All changed executable lines and business/security branches require the existing coverage evidence; no fabricated commands, skips, ignores or weakened assertions. An HTTP script is not a rendered role journey; a mock is not real provider delivery. Consider all applicable 19 adversarial categories and actual user back/stale/double-click/offline/mobile/keyboard behavior. Keep production out of mutation, seeding, load and vulnerability tests.
5. Freeze and record the task revision. A separate senior reviewer assesses correctness, specification/approved-rule fit, architecture, tenant/security boundaries, migration/contracts, maintainability and missing tests; use a specialist for the actual risk. Separate QA derives cases from requirements/source and checks actual execution evidence, changed branches and affected real-user journeys. Record every finding with source, failure mechanism, severity, fix and verification. The lead adjudicates disagreements using evidence, not blind acceptance.
6. Fix valid findings, add regressions, rerun affected checks and obtain scoped re-review at the new head. Continue while evidence or code changes make progress. Unrelated suggestions go to the backlog. Repeated identical failure/no new evidence requires root-cause replanning or a named blocker, not an endless retry/review loop. A round limit never converts an unresolved material finding into a pass. Stop the task's loop when approved cases, required coverage/boundary/browser gates and independent review are complete; do not chase unspecified product perfection forever.

## 4. Branches, Stacks And PRs

- Each implementation task has its own `sprint-<work-date-sprint>/<artifact-id-or-short-purpose>` branch and focused commits. Start independent tasks from the freshly fetched origin/release-01 in isolated worktrees. Use live sprint dates and preserve existing task IDs/owner-approved historical allocation.
- The owner explicitly permits stacked branches for dependent tasks. Record the precise parent branch/head and fork point; implement only the child's slice and show both task-local and cumulative release-01 diffs/verification. Do not hide prerequisite commits in a supposedly independent PR.
- Every task PR targets **release-01**, including stacked PRs. Publish dependent PRs as draft until their prerequisites are merged/reconciled and their own gates pass. State dependencies, migration/API/config ordering and do-not-merge-before constraints prominently. Independent PRs may become ready after their own gates. No empty PR for an epic or a previously completed discovery record.
- Before publication, verify branch contents, target base, generated outputs, meaningful commit messages, sanitization, current review/test head and required CI. The PR states problem/result, approved rules, task/case links, exact validation/evidence, dependency/merge position, migration/config and rollback risks. Watch actual CI results; a created PR or a green local build is not complete verification. Missing hosted credentials or checks remain explicit blockers/drafts where required.
- The owner merges PRs. After each observed merge, fetch and identify its actual result; reconcile dependent branches using recorded ancestry, including squash-merge/rebase changes. Do not blindly rebase by HEAD~1 or duplicate predecessor changes. Recheck task-local/cumulative diff, migrations/contracts, affected tests and independent review at the new head. Rewriting a task branch requires activation authorization, exclusive ownership and force-with-lease if needed; never force protected/shared branches or erase someone else's work.
- A disposable local integration worktree may rehearse the dependency order; it is not an owner merge into release-01 and does not replace post-merge regression. Do not merge protected branches, enable auto-merge or promote/deploy main under this workflow.

## 5. Handoff, Owner Merges And Release Gate

Distinguish development/testing complete, PR draft, PR ready for owner merge, merged/pending integration regression, regression passed, human QA/UAT pending and release approval pending. Use the live sheet's supported status values and explicit notes for finer states. Do not label planning, blocked tests or unavailable independent review Done. Ready for a QA team does not mean human QA, penetration testing or production certification occurred.

When all currently actionable tasks have reviewed/tested PRs, give the owner a topologically ordered merge table: position, task, branch/PR URL, depends-on PRs, migration/config order, evidence, exact gate before/after merge, known blockers and rollback. Identify independent groups and the first safe merge, then pause only the steps needing owner action while continuing genuinely independent work. Do not call the overall release goal complete while required tasks, owner merges or regression remain pending.

After each owner merge, verify actual release-01 at its new SHA using affected smoke/role/tenant/contract/data/worker cases. Fix regressions on a new task branch/PR to release-01, then rerun relevant checks. After the full set is merged, run the documented full gate and deep integrated regression: role journeys, cross-company denial, stale sessions, concurrency/idempotency/rollback, office/calendar/payroll history, uploads/exports, offline recovery, worker/queue and approved provider/storage boundaries as applicable. Use measured safe capacity/recovery scenarios only within authorized environments; external penetration and actual-role human UAT remain explicitly separate requirements.

Notify the owner of release readiness only with exact tested release-01 SHA, completed cases/reviews, migrations/config/rollback, secret readiness and remaining risk/approvals. Missing required human/provider/hosted evidence means conditional handoff with named gaps, not ready to ship. The owner decides and performs main promotion; do not merge main or deploy. Report only readiness supported by actual evidence.

## 6. Credentials And Skills

Use [credential register](../agent/credential-register.md). Discover exact variable names and required scopes from tracked source/examples and authorized provider docs/CLI, then check existing approved stores/local configuration without printing values. Prefer a legitimate local emulator/container where it tests the needed contract, and label simulated versus real verification. Never invent a key or claim an encrypted store's unavailable value was retrieved. Ask only for missing owner actions such as account/domain verification, new security-sensitive credentials, payment or access; keep independent work moving.

Use existing stores and ignored local environment files for values, verify ignore rules before any local save, and never record secrets in git, sheets, PRs, chat, logs or screenshots. The register contains key names, purpose, environments, scope, approved location, task/owner, readiness and non-secret verification only. No production secret reuse, broad permission expansion, new paid account or hosted configuration is implicitly authorized.

Reuse existing project skills first. For a genuine gap, use find-skills: inspect the leaderboard, candidate source/reputation/adoption, compatibility and referenced helpers before recommending adoption. Popularity is not correctness. Respect local business/QA/environment/authorization rules over external recipes. Prefer a focused local workflow refinement when it fits; do not install or run an unreviewed helper, force a model/provider or introduce a parallel framework solely because it is popular. Record useful improvements in the agent/workflow docs and tracker with source-backed scope, not an uncontrolled new feature list.
