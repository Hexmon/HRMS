# Cloudflare background worker cutover (not yet executed)

This runbook replaces only the long-running Render background worker. Vercel still hosts the frontend, Render still hosts the Fastify API, Neon remains the PostgreSQL source of truth, and Upstash Redis remains required for sessions and rate limiting. Do not interpret a successful local test or Worker bundle as evidence that a hosted cutover has happened.

## Current and intended behavior

| Path | Before cutover | After cutover |
| --- | --- | --- |
| Outbox creation | API services append through `expenses/events.ts` or `core/events.ts` (used by admin, assets, documents, EMS, expenses, leave/WFH, projects, reports, timesheets, and attendance), plus direct SQL in attendance command/service and platform repository. `postgres-data-store.ts` persists memory-backed rows. | Same producers and PostgreSQL rows; API sends a best-effort post-commit drain signal, with one-minute Cron recovery. |
| Outbox delivery | `run-outbox-worker.ts` polls forever and `outbox-worker.ts` publishes `hrms.*` Redis Streams. | `cloudflare-jobs.ts` drains 50 due rows per Queue invocation, sends only durable `event_id` to the event Queue, then marks rows published. The consumer re-reads PostgreSQL. No business-event side effect is added because this repository has no Streams consumer. |
| Attendance automatic checkout | Render polling worker repeatedly scans sessions. | Five-minute UTC Cron enqueues bounded, cursor-based 25-session sweeps. The existing transactional attendance command evaluates each company's timezone/policy and takes row locks; duplicate sweeps must not make duplicate checkout punches. |
| Coordinate cleanup | Render polling worker calls transactional 500-row purge. | Hourly UTC Cron enqueues the same purge, with continuation jobs if a full batch remains. |
| Reads | API attendance pages, dashboard and reports historically used a process-start snapshot even after another process wrote attendance. | Request-local company-scoped attendance reads fetch committed punches and daily records for affected GETs and attendance exports. Dashboard pending-outbox counts, report-export status, and active-company audit rows also read committed rows. The audit route checks current role, employment and company state from the same PostgreSQL snapshot. Other process-snapshot readers still need review before release signoff. |

Repository search found no `XREAD`/`XGROUP`/`XACK` consumer. The owner stated on 2026-10-23 that no external `hrms.*` consumer is running. Reconfirm this for the target environment at cutover; a newly introduced external consumer changes the migration plan.

## Provision one isolated environment at a time

1. Obtain a Cloudflare Workers Paid account and credentials through the approved secret store. Provision a separate Worker, two source Queues, two DLQs, and a separate cache-disabled Hyperdrive configuration for each `dev`, `qa`, and `production` environment. Do not reuse a Neon branch or Queue across environments. The checked-in zero Hyperdrive IDs are placeholders and cannot be used for deployment.
2. Create Hyperdrive against the matching Neon branch using Cloudflare's `--caching-disabled` option (or dashboard equivalent). Verify the resulting configuration shows caching disabled; Hyperdrive does not invalidate cached reads after writes, which would break the outbox and attendance scans. Keep the Neon connection string out of shell history and repository files. Hyperdrive uses `pg`; do not add advisory locks to these jobs. See [Hyperdrive caching](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/) and [supported features](https://developers.cloudflare.com/hyperdrive/reference/supported-databases-and-features/).
3. Create the environment's Queue names from `hrms_backend/wrangler.jsonc`. Configure the two DLQs' retention to the agreed operational window before starting traffic; the default unconsumed DLQ retention is four days. On Workers Paid, Queue retention can be configured up to 14 days. Check the desired jurisdiction matches between each source Queue and its DLQ. See [Queue configuration](https://developers.cloudflare.com/queues/configuration/configure-queues/) and [DLQs](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/).
4. In the matching GitHub environment (`development`, `qa`, or `production`), set `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `HRMS_HYPERDRIVE_ID`, and `OUTBOX_SIGNAL_TOKEN` as secrets. The token must also be set as `OUTBOX_DRAIN_TOKEN` on the matching Render API. Never place any of these values in the tracked Wrangler file.
   If this environment never had a Render polling worker, set its GitHub variable `DEV_RENDER_LEGACY_WORKER_PRESENT`, `QA_RENDER_LEGACY_WORKER_PRESENT`, or `PROD_RENDER_LEGACY_WORKER_PRESENT` to `false` so pre-cutover API deploys do not require a nonexistent worker hook. The default remains fail-closed and requires that hook when the variable is unset.
5. Run the manual **Deploy Cloudflare background worker** workflow with `state=inactive`. This deploys the isolated Worker with Cron and Queue handlers disabled, then installs the token secret. Check `/health` returns `active:false`. Use the authenticated `GET /internal/lag` endpoint to confirm the Worker can query the intended Neon branch. Keep the Render polling worker running at this stage.

Before activation, apply backend migration `0064_attendance_open_session_sweep_index.sql` through the normal Render pre-deploy migration path on that same Neon branch. Verify `attendance_sessions_open_sweep_idx` exists on `attendance.sessions (checked_in_at, id)` for open, nondeleted rows. The repository migration runner executes SQL in a transaction, so this index is built **without** `CONCURRENTLY` and may block writes after acquiring its lock; the five-second lock timeout limits lock acquisition, not index-build duration. Measure the build on a production-sized staging copy, obtain a reviewed low-traffic window and rollback plan, then apply it before activation. If the table is too large for that window, first add a reviewed nontransactional/concurrent-index migration path rather than running this migration on live Neon.

Local development uses `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE` with `pnpm exec wrangler dev --var WORKER_ACTIVE:true` and the Docker PostgreSQL database. The checked-in root and all named Wrangler environments default to inactive; only the reviewed active deployment workflow or this explicit local override enables processing. Local Hyperdrive emulation does not prove production Hyperdrive caching or Neon connectivity. See [local Hyperdrive development](https://developers.cloudflare.com/hyperdrive/configuration/local-development/).

The frontend production bundle is built on the Linux host and packaged into its runtime container (the local Docker VM lacks the memory to bundle it internally). The stack starts a separate PostGIS database, Valkey, seeded API, local Wrangler Queue/Cron emulator, frontend server, and Playwright browser. It uses synthetic users and local secrets only. The browser test advances the scheduler reference time to make a checkout due; it does not alter the browser or database clock. Review the local, git-ignored `hrms-client/playwright-report/index.html` for retained successful screenshot attachments and the Worker/API logs for processing evidence; `hrms-client/test-results` contains failure artifacts only. Keep or export the report separately if evidence must outlive this workspace. Stop the stack with `docker compose -f hrms_backend/infra/docker/docker-compose.cloudflare-e2e.yml -p hawkaii_hrms_cloudflare_e2e down` when finished; this preserves its named database volume. The attendance browser cases consume a same-day session and require a fresh synthetic database for another full run. After confirming the exact project contains only synthetic data, `down -v` deletes its named volume and the next `up` reseeds it; the deleted test data cannot be recovered. It must never be configured with hosted Neon or Upstash credentials.

Backend CI also runs `pnpm verify:cloudflare-queue-dlq`: it bundles the real Worker and checks local Queue retry exhaustion, healthy-message isolation, DLQ receipt, and same-body replay after a missing PostgreSQL event is repaired. The command rejects non-local or non-`*_test` database URLs. Its local DLQ observer acknowledges test messages on receipt; it does not replace the hosted operator drill, including inspection and acknowledging the original DLQ message **after** successful replay.

## Cutover order and reconciliation

1. Record a UTC cutover start time, the deployed API and Worker revisions, source/DLQ backlog metrics, the authenticated `/internal/lag` response, and a PostgreSQL snapshot of `platform.outbox_events` grouped by `status`. Verify the API health `build_sha` identifies the actual deployed commit (the currently hosted dev API reports `dev`, which is not a release identifier); do not rely on a placeholder for rollback selection. Preserve the event IDs in `pending`, `retry`, and `dead_letter` and any `published` rows in the overlap window. Do not copy event payloads into tickets or logs.
2. Stop or scale to zero the old Render polling worker; verify its process is actually stopped. If no Render worker was ever deployed, record that evidence. Disable the old service's automatic deploy/restart path in Render before activation, and verify a later API deployment does not bring it back. The checked-in `render.yaml` still declares that legacy worker for a reviewed rollback window; do not sync the Blueprint in a way that silently starts it. Do not delete the old service yet. The API must remain available.
3. Run the manual Worker workflow with `state=active`, entering its explicit cutover confirmation. Verify `/health` reports `active:true`; trigger `POST /internal/outbox-signal` with the shared bearer token and expect `202`. Set Render API `OUTBOX_DRAIN_URL` to the deployed Worker `/internal/outbox-signal` URL, with its matching `OUTBOX_DRAIN_TOKEN`. Set `HRMS_EVENT_TRANSPORT=cloudflare` for release-adapter verification. Set the per-environment GitHub variable `DEV_HRMS_CLOUDFLARE_CUTOVER_ACTIVE`, `QA_HRMS_CLOUDFLARE_CUTOVER_ACTIVE`, or `PROD_HRMS_CLOUDFLARE_CUTOVER_ACTIVE` to `true` so future CI deploys do not restart the legacy worker.
4. Run the API readiness probe and the release-adapter smoke. Wait for pending/retry rows to drain or document each retry reason. Confirm the Queue event consumer logs the smoke `event_id`. Compare the source Queue and DLQ backlog metrics with the pre-cutover snapshot. A `published` row means Queue acceptance, not completion of any external business consumer.
5. If the old worker published rows to Redis Streams during the overlap, reconcile their event IDs from PostgreSQL and enqueue selected `{"kind":"event","eventId":"<UUID>"}` JSON messages to the matching event Queue via the Cloudflare dashboard. Replays are allowed to duplicate an `event_id`; consumers must be idempotent. Retain the reconciliation list and result as QA evidence.
6. Observe at least one natural one-minute outbox Cron, one five-minute attendance Cron, and one hourly coordinate cleanup Cron before calling the hosted run verified. Schedules are UTC; the attendance command still uses company-local policy time. Have human testers repeat the employee, manager, HR, and admin journeys and attach browser, DB, Queue and log evidence.

## Monitor and recover

- Poll authenticated `/internal/lag` for outbox pending count/age, database dead-letter rows, open attendance sessions, and expired unpurged coordinate rows. These are indicators, not a business-approved SLO. Also monitor Cloudflare Queue and DLQ backlog count/oldest message age, Worker errors/retries, Hyperdrive/Neon connection saturation, and Render API post-commit signal warnings. Set alert thresholds with the SRE owner before release.
- For a transient Queue or Neon outage, do not edit the database immediately. The configured per-message Queue retries and one-minute/five-minute/hourly Cron sweeps provide recovery. Record the first failure, last successful processing time, and whether the next scheduled run caught up.
- For a database `dead_letter` outbox row, investigate `last_error`, correct the cause, and obtain operator approval for a narrowly scoped transaction resetting only reviewed event IDs to `status='retry', retry_count=0, available_at=now()`. Signal the outbox drain and verify those exact IDs become published. Never bulk-reset all dead-letter rows.
- For a Cloudflare DLQ message, inspect its body and attempt history in the dashboard. Fix the cause; send that same validated JSON body to its source Queue; verify the new processing log, DB state and user-visible result, then acknowledge only the original reviewed DLQ message. Acknowledgement permanently removes it. See [listing/acknowledgement](https://developers.cloudflare.com/queues/examples/list-messages-from-dash/) and [sending](https://developers.cloudflare.com/queues/examples/send-messages-from-dash/). If the message is an attendance/purge job, prefer a fresh scheduled job over replaying an old attendance `referenceIso` without reviewing the intended cutoff.
- A backlog of old `published` rows is not fixed by re-running the drain: it selects only `pending`/`retry`. Reconcile exact event IDs and replay to the event Queue only after confirming the destination consumer's idempotency.
- Report-export events created before the company-scoped metadata change have no immutable `company_id` in their payload. Their metadata is deliberately hidden, including from admins, to avoid exposing a former company's export after a user transfers. If historical exports must remain accessible, review and backfill exact event IDs against their original company using audit evidence; do not infer company from the creator's current session preference.

## Rollback

Pause delivery on both source Queues first (`wrangler queues pause-delivery <queue-name>`; see [pause delivery](https://developers.cloudflare.com/queues/configuration/pause-purge/)); verify the pause in the dashboard. This prevents an inactive Worker from consuming retry attempts while preserving queued messages. Deploy the Cloudflare Worker with `state=inactive` and verify no new jobs execute. The inactive handler defers any in-flight delivery by one hour as a fallback, but that is not a substitute for pausing the Queues.

If Redis Streams are still available and no incompatible event consumer was introduced, restore the old Render worker from its last known-good deploy and set the per-environment GitHub cutover variable back to `false`. Keep the API's failed Cloudflare signal best-effort; Cron is inactive and the old worker resumes pending rows. Compare outbox statuses and attendance checkout counts before and after rollback. Do not revert forward-only migrations or delete Queue/DLQ messages during the incident. If Redis Streams are unavailable, do **not** claim this rollback path is safe: keep the Worker path and repair/replay from PostgreSQL/Queues instead. Resume Queue delivery only after a reviewed active Worker is ready to process its backlog; Queues continue to retain messages while paused, subject to their retention period.

Release remains blocked until hosted deployment, reconciliation, DLQ/rollback drill, full automated gates, and human UAT evidence are recorded.
