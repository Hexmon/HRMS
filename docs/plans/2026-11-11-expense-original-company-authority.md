# Expense Original-Company Authority And Receipt Integrity

## Objective And Success Criteria

- Objective: make direct expense ticket reads, approvals, payment, settlement and receipt links depend on the ticket's durable original company and the actor's current authority.
- User outcome: a current authorized Finance approver at company A can finish A's pre-transfer expense; company B and stale/revoked roles cannot act on it; the requester can see their own historical expense when a durable requester identity links them to it.
- Success: no foreign-company detail, receipt, audit, payment or mutation is returned or committed; approved actions update ticket, child rows, audit and outbox atomically; denied/failed actions leave no object bytes or orphan links; a second instance sees the committed result.

## Scope

- In scope: expense-owned company field/backfill/quarantine, direct route authorization, current-role checks, related IDs, versioned SQL command and receipt authorization/storage coordination, required UI behavior and tests.
- Out of scope: DEC-024 arithmetic redesign and DEC-BQ09 payment cap/currency/proof decisions; generated report export materialization (TEN-S25-008/R2); general document storage redesign beyond expense parent links (TEN-S25-021); global ticket sequence isolation (TEN-S25-024).
- Roles/tenants: Employee/requester, Manager, Finance, HR, Auditor, Admin in two synthetic companies and an approved A-to-B transfer. Local disposable PostgreSQL and memory unit tests only; no hosted mutation or browser use until permission is available.

## Risks, Compatibility And Recovery

- Every historical ticket remains quarantined because neither legacy JSON nor the requester audit proves the original company. New writes must never omit owner. Before hosted cutover, count `owner_resolution_status='quarantined'` by reason and reconcile each ticket against independent creation evidence in a separate reviewed forward migration with immutable audit; do not infer ownership from current department or employment. The ordinary app role must not acquire an owner-repair endpoint.
- Migration 0068's row triggers require a transaction-local `app.expense_command_v1` marker on `expense_tickets`, `expense_line_items`, `expense_approvals`, `expense_audit_logs`, `expense_documents`, `expense_payments`, `employee_reviewer_mappings` and `expense_policy_rules`, fencing old response-end full-store DML even for the same company. The marker is only an old-writer fence, **not actor authorization**; new commands must independently lock/check current actor/company/role, parent owner/version and related IDs in the same transaction. The local migration verifier checks marker absence after commit and rollback on connection reuse. Old binaries must drain before hosted migration/cutover. A new SQL command must bypass exactly its own old response-end expense flush. A forward recovery is safer than old-binary rollback after changing write semantics. TRUNCATE/table-owner privileges and audit-table repair privileges need separate runtime/migration roles before release.
- Authorization must precede object storage. If storage succeeds but SQL commit fails, record a bounded reconciliation/cleanup path and do not report business success.
- The SQL-mode receipt deny uses a separate ID precheck and existing global document service; it is safe only while the path remains denied. Enabling it requires one request-local parent/document authorization snapshot or transaction to eliminate TOCTOU. Generic multipart upload can buffer before the `business_object_type` guard, so size/resource limits remain a QA gate.
- Finance command results retain only ticket ID, status and version, keyed by company, current actor, action and client intent key; a different request hash cannot reuse the key. No automatic purge is configured: retention, archival tombstones, runtime access privileges and at-rest protection need approval before release. The frontend retains a pending key in session storage across uncertain response loss; it does not persist payment details in the key. A later deliberate action rotates the key after confirmed success.
- Pending-company `/auth/me` is read-only and intentionally does not mint or expose a bootstrap token. Production/multi-instance bootstrap completion therefore still needs a separate AUTH-owned durable resume/rotation transaction and UI handoff; this expense branch must not pretend `setup_required` alone can complete onboarding. Existing SQL login/password/preference mutation gaps are separate pre-existing AUTH P1s and were not expanded into this task.
- Narrow request-local SQL projections keep current-company expense reports, the durable requester's own typed historical expense report, the general dashboard's typed expense/outbox counters, notification list/count reads, and target-scoped mark-read/read-all writes immediately consistent after a Finance commit without mutating or reloading the shared process store. Attendance dashboard evidence uses a rolling company-calendar 12-month window with a maximum 10,000 visible days and 50,000 related rows per evidence source, errors before truncation, and delegates categorization to the canonical attendance helper. Expense report audiences and supported filters are applied in SQL before the 1,000 matching-ticket and 10,000 matching-child bounds. Report export authorization/persistence remains a separate blocker. Notification writes are bounded, idempotent and transaction-owned.
- The memory-only Finance command replay map is capped at 10,000 results per isolated store and fails closed at capacity rather than evicting a replay record. PostgreSQL remains the production command-result store; retention/archival for its durable table is still an operational decision.
- DEC-024 settlement arithmetic remains an existing release blocker. The follow-up does not claim to correct its payable/recoverable calculation, caps, currencies or proof requirements; successful transaction and freshness tests only exercise the currently implemented arithmetic.
- Owner repair now requires an audit-first immutable evidence row, a transaction-local repair marker and a matching ticket/company/original-context relationship, with deferred final-state validation. The marker is a fence, not authorization: deployment must use a dedicated migration role allowed to insert repair evidence, while the application runtime role must not receive that privilege.
- Settlement now checks verified receipt links against live matching finance document metadata and its current version in the command transaction, with row locks. This checks SQL referential consistency, **not the existence or privacy of object bytes**. R2-S25-001/TEN-S25-021 private storage and byte verification remain release blockers; a fabricated metadata/version row cannot substitute for a stored private receipt.
